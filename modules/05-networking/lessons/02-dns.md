# DNS and Name Resolution

## Why this matters

The rehearsal failed with "could not connect to database server db". The
database was fine; the client simply couldn't translate the name `db` into
an IP address. Name resolution is the most common cause of "the network is
broken" reports — and one of the easiest to check.

## Concepts

### Names and addresses

Computers connect to IP addresses; humans prefer names. **Name resolution**
is the translation from one to the other. On Linux, programs ask the C
library (`getaddrinfo()`), which follows the rules in
`/etc/nsswitch.conf`:

```text
hosts:          files dns
```

This line means: first look in **files** (`/etc/hosts`), then ask **DNS**.

### `/etc/hosts`: the local list

```text
127.0.0.1    localhost
10.10.2.20   db01 db01.company.local
```

One IP per line followed by one or more names. Entries here win over DNS
(given the order above), take effect immediately, and only affect this one
machine. Perfect for quick fixes and tests; painful to maintain across a
hundred servers — which is why DNS exists.

### `/etc/resolv.conf`: which DNS server to ask

```text
nameserver 10.10.1.53
search company.local
```

- `nameserver` — the IP address of a DNS server (up to three lines).
- `search` — domains to try appending to short names. With
  `search company.local`, looking up `db` also tries `db.company.local`.

On many desktops and servers this file is generated by systemd-resolved or
NetworkManager; on the lab containers Docker generates it, and you can edit
it directly.

### DNS records

A DNS server stores **records** for its zones (here `company.local`):

| Type | Maps | Example |
|---|---|---|
| A | name → IPv4 address | `db.company.local → 10.10.2.20` |
| AAAA | name → IPv6 address | `web01 → 2001:db8::80` |
| CNAME | alias → canonical name | `www → web01.company.local` |
| MX | domain → mail server (with priority) | `company.local → 10 mail.company.local` |
| TXT | name → arbitrary text (SPF, verification) | |
| PTR | IP → name (reverse lookup) | `20.2.10.10.in-addr.arpa → db` |

Each answer carries a **TTL** (time to live): how many seconds resolvers may
cache it.

### Query tools

| Command | Use |
|---|---|
| `getent hosts NAME` | resolve **exactly like applications do** (files, then DNS) |
| `dig NAME [TYPE]` | detailed DNS query; `+short` for just the answer, `@SERVER` to pick a server |
| `nslookup NAME [SERVER]` | older, simpler DNS query tool |
| `host NAME` | short, friendly output |

`dig`, `nslookup` and `host` talk to DNS directly and **ignore
`/etc/hosts`**. `getent` is the one that shows what an application will
actually get.

### Running a DNS server

The lab's `dns` machine runs **dnsmasq**, a small DNS (and DHCP) server. Its
whole zone is a few lines in `/etc/dnsmasq.conf`:

```text
local=/company.local/
host-record=db.company.local,db01.company.local,10.10.2.20
cname=www.company.local,web01.company.local
mx-host=company.local,mail.company.local,10
server=127.0.0.11
```

Anything outside `company.local` is forwarded to the `server=` upstream.
Larger setups use BIND, Unbound, PowerDNS or CoreDNS, but the concepts are
the same.

## Try it

These run on the lab `client`.

Which sources are consulted, and in what order?

```bash
grep '^hosts' /etc/nsswitch.conf
grep -v -e '^#' -e '^$' /etc/resolv.conf
```

```text
hosts:          files dns
nameserver 127.0.0.11
options timeout:2 attempts:3 ndots:0
```

The client currently uses Docker's built-in resolver, which knows about
containers on its own networks (like `web01`) but nothing about
`company.local`:

```bash
getent hosts web01
getent hosts db.company.local || echo "not resolvable"
```

```text
10.10.1.80      web01
not resolvable
```

Ask the company DNS server directly with `dig` and friends:

```bash
dig @10.10.1.53 db.company.local +noall +answer
dig @10.10.1.53 www.company.local +short
dig @10.10.1.53 company.local MX +short
host db.company.local 10.10.1.53 | tail -1
```

```text
db.company.local.	300	IN	A	10.10.2.20
web01.company.local.
10.10.1.80
10 mail.company.local.
db.company.local has address 10.10.2.20
```

`/etc/hosts` wins over DNS for applications, but `dig` ignores it. (Docker
bind-mounts `/etc/hosts` into the container, so tools that *replace* the
file, like `sed -i`, fail with "Device or resource busy"; editors and `tee
-a` work.)

```bash keepoutput
cp /etc/hosts /tmp/hosts.bak
echo "10.10.9.99 web01" | sudo tee -a /etc/hosts
getent hosts web01
dig @10.10.1.53 web01.company.local +short
sudo tee /etc/hosts < /tmp/hosts.bak > /dev/null
getent hosts web01
```

```text
10.10.9.99 web01
10.10.9.99      web01
10.10.1.80
10.10.1.80      web01
```

## Common mistakes

- **Testing with `dig` and assuming the application sees the same.** `dig`
  skips `/etc/hosts`; use `getent hosts` to see what apps get.
- **A stale `/etc/hosts` entry** overriding correct DNS, long after the
  server moved. Check it first.
- **Forgetting the trailing dot meaning.** In zone files `web01.company.local.`
  with a dot is absolute; without it the zone name may be appended.
- **Putting a hostname in `nameserver`.** It must be an IP address — you
  can't use DNS to find the DNS server.

## Recap

- `nsswitch.conf` sets the order (`files dns`); `/etc/hosts` is the local
  list; `/etc/resolv.conf` names the DNS servers and search domains.
- Records: A, AAAA, CNAME, MX, TXT, PTR, each with a TTL.
- `getent hosts` = what applications see; `dig`/`nslookup`/`host` query DNS
  only.
